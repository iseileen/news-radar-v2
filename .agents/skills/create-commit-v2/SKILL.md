# Create Commit（提交變更）

依這門課的提交訊息慣例，把使用者目前的變更完成一次提交（commit）。

## 提交訊息格式

格式：`類別: 中文描述`（英文類別＋半形冒號＋一個空格＋中文描述）

1. 類別（四選一）：`feat`、`fix`、`docs`、`chore`——意思與分支類別相同，只是 `feature` 在提交訊息裡慣例簡寫成 `feat`。
2. 描述用中文、動詞開頭，一句話講清楚「這次改動做了什麼」，讓人不用開啟程式碼也大致看得懂。
3. 一次提交只講一件事。如果訊息想寫出「順便」兩個字，代表這次提交混了不只一件事。

## 執行步驟

1. 先用 `git status` 與 `git diff` 看清楚這次實際改了什麼；若發現和任務無關的變更混在裡，先向使用者確認要不要一起提交。
2. 把變更加入暫存區（staging area）：`git add .`（或只加入相關檔案）。
3. 依「實際的變更內容」產生提交訊息（不是依使用者的原話照抄），執行 `git commit -m "訊息"`。
4. 回報這次使用的提交訊息，讓使用者確認格式與內容。

## 使用者要求連同推送時

**只有使用者自己開口要推**（例如「直接推上 main」「提交完順便推上去」）才做這一段；他沒說就停在上一步。

1. 先確認本機和遠端的關係：`git fetch` 之後看 `git status`。
2. 只要不是「和遠端一致」就先同步，**落後（behind）和分歧（diverged）都算**——剛建立完提交的當下多半是分歧，因為兩邊各有對方沒有的東西：

   ```
   git pull --no-rebase
   ```

   這個專案的 workflow 會自己把紀錄提交回儲存庫，所以本機跟遠端對不上是常態，不是出事——這個狀態下推不上去。`--no-rebase` 是用合併（merge）的方式接上，分歧的情況下 `main` 上會多一筆合併提交，那是正常的。同步過程若出現需要人工處理的衝突，停下來回報，不要自己解。
3. 把即將執行的指令列給使用者確認，使用者確認之前不要執行：

   ```
   git push
   ```

4. 執行後回報推上去的分支與提交。

## 不要做

以下的事不在這個 skill 的範圍內。提交完成、回報完訊息（使用者有要求推送的話，推完回報完），這次任務就結束了，下一步等使用者開口：

- **使用者沒有要求就不要推送（push）**，也不要開分支或發拉取請求。
- 不要主動修改或補寫任何檔案內容；這個 skill 只負責把「已經改好的東西」提交起來。
- 不要用改寫歷史的方式補救（例如 `git commit --amend`）；訊息或內容有誤，告訴使用者後用一次新的提交修正。
- 只執行這些指令：`git status`、`git diff`、`git add`、`git commit -m`、`git log`、`git fetch`、`git pull --no-rebase`、`git push`。清單以外的 git／gh 指令一律不執行（`git config` 也在清單之外，不要用它改設定來繞過同步問題）。

## 範例

好的提交訊息：

- `feat: 將 W1 進度標記為完成`
- `fix: 修正登入按鈕顏色`
- `docs: 補充 README 安裝說明`

不好的提交訊息：

- `update`、`修好了`（看不出改了什麼）
- `改了 data.js`（只講動到哪個檔案，沒講做了什麼事）
- `標記完成順便修了排版`（一次講了兩件事）
